1 · Universal rules — cipher, encoding, newline

The single most useful fact. Every Kaguya text container, both branches, 2001 to 2026, encrypts with XOR 0xFF. tblstr.arc calls it complement; message.dat stores 0xFF as its XOR key in the header. What changed across 25 years is where the text lives and what else is encrypted beside it — never the cipher.
ItemRule
Cipherb ^ 0xFF, identical to bitwise NOT ~b. Encryption and decryption are the same operation.
Text encodingCP932 (Shift-JIS with Microsoft extensions). Two exceptions: ver4 voice filenames are UTF-16LE.
Newline0x0A. In an encrypted tblstr payload you see 0xF5 (0x0A ^ 0xFF).
Intermediate filesUse UTF-8 for your own JSON/TSV and convert back to CP932 on reinsert.
Do not hardcode the XOR key for message.dat. The encryption flag and the key are real header fields (offsets in §2). Every sampled file happens to use 0xFF, but read the bytes. When the flag is zero the payload is plaintext.

3 · Branch A — tblstr.arc

A flat table of strings. Script bytecode in scr.arc points into it. All text is XOR 0xFF. The four types differ only in framing, terminators, padding, and how the script finds an entry.

Geometry at a glance

TypeMagicFile headerEntry headerPayload
0a 0b none 4 B — u32 str_max_addr 8 B — u32 type, u32 len ~text + raw 0x00 terminator + 0x00 padding to a multiple of 4. Records 4-byte aligned.
1 [STRTBL] 16 B, preserved verbatim 6 B — u32 id, u16 len ~(text + 0x00) + 0xFF padding. len = round_up_4(len(text)+1+6) − 6
2 UF01 8 B — magic + u32 index_pos 8 B — u32 type, u32 len ~text only. No terminator, no padding, no alignment. A u32[] of absolute record-header offsets sits at EOF.

Record types (Type 0 and Type 2): 0 = message, 2 = speaker name, 3 = choice. Type 1 stores no type field — everything parses as a message and is reclassified by reading the script.

Verified across all 76 tblstr files: zero misaligned records, zero incomplete record walks, zero Type 1 padding deviations, zero Type 2 index-table gaps, zero out-of-bounds Type 2 indices. Type 1 header count equals parsed count in 6/6; the Type 1 header unknown field is 0x00000001 in 6/6; entry id runs sequentially from 0 in 6/6.

3.1 Type 0 (raw, no magic)

File header (4 B)
  u32 str_max_addr        // total size of the string area = end of the last record

Records × N, contiguous, starting at offset 4
  u32 type                // 0 = message, 2 = name, 3 = choice
  u32 len                 // length of content; always a multiple of 4
  u8  content[len]
        = ~text                        // XOR 0xFF
        + 0x00                         // terminator: RAW byte, NOT encrypted
        + 0x00 ... pad to a multiple of 4   // builder residue, not guaranteed zero

[str_max_addr .. EOF]     // trailing bytes; preserve verbatim

Decoding one record

nul  = indexOf(content, 0x00)          // search the UNDECRYPTED bytes
body = (nul >= 0) ? content[0..nul] : content
text = cp932_decode( xor_ff(body) )
// For type == 0, extraction commonly strips a trailing '\n' and re-adds it on write.

Encoding one record

enc   = cp932_encode(text)             // re-add '\n' first if the original had one
block = xor_ff(enc) + [0x00]
while (block.length % 4 != 0) block += 0x00
emit: u32 type, u32 block.length, block
Three rules that matter:
  1. Record starts are 4-byte aligned. Because the record header is a fixed 8 B and payload length is a multiple of 4, this holds automatically if you follow the encoder above.
  2. Type 0 padding is builder residue and is not necessarily zeros. For records you did not translate, re-emit the original bytes rather than regenerating padding. The same applies to the 16-byte STRTBL header and to any trailing bytes after the string area.
  3. Encoded text must not contain 0xFF. After complementing it becomes a raw 0x00 and the record truncates there. Refuse the write and keep the original bytes.

The 0x14-header variant

Eight Type 0 titles use a 20-byte file header whose bytes 4–19 form a virtual type-2 record (type=2, len=8).

// Detection
if (fileSize >= 0x14 && u32@4 == 2 && u32@8 == 8) → 0x14-header variant

// Handling: nothing special is required.
// Walk records from offset 4 unconditionally. The virtual record round-trips as an
// ordinary record and script references to it resolve correctly.

Observed in 女教師 (DVD ED.), ダンジョンクルセイダーズ, で・る・た！, はらハラしちゃう！朝霧姉妹編, ミニパイくれ〜ま〜, 熟バレー, ユリキラー — spanning 2005 to 2015 across four teams, so treat it as a per-title build option, not an era or team marker.

3.2 0a vs 0b — the one thing the header will not tell you

Both sub-modes are byte-identical containers. The difference is what the number at 13 0C +8 in the script means.

0a direct-offset0b ARI-index
text_id meansbyte offset of a type-0 record header1-based index into the ARI table
Length-changing rebuildmust re-patch every text_idtext_id is stable; the ARI is rebuilt instead
tblstr.ariabsentpresent, count = #type-0 + 1
Build era2001-06 → 2004-122005-02 → 2015-05

Reliable detection

// 1) Build a record map from the container
records_by_offset = { offset → type }      // walk from offset 4 to str_max_addr
msg_count         = number of records with type == 0

// 2) Scan scr.arc for candidate 13 0C instructions
for each pos where scr[pos]==0x13 && scr[pos+1]==0x0C && scr[pos+2]==0x00 :
    name_offset = u32 @ pos+4
    text_id     = u32 @ pos+8

    // 3) Validate name_offset FIRST — this is the false-positive filter
    if (name_offset != 0xFFFFFFFF) and
       (records_by_offset[name_offset] missing OR its type != 2):
           skip this instruction

    // 4) Classify the surviving text_id
    is_index  = (1 <= text_id <= msg_count)
    is_offset = records_by_offset[text_id] exists AND its type == 0

    tally into: index_only / offset_only / both / neither

// 5) Verdict — "both" is EXCLUDED
offset_only > 0 and index_only == 0   -> 0a (direct)
index_only  > 0 and offset_only == 0  -> 0b (index)
both > 0 (values on each side)         -> majority; tie goes to 0a
neither                                -> inconclusive; fall back to ARI presence
Why both must be discarded. A record at byte offset 44 in a file with at least 44 messages is simultaneously a valid index and a valid offset, so it carries no information. This bucket is never empty in practice (56–629 instructions per title), which is exactly why excluding it matters.
45 of 46 Type 0 titles resolve unanimously from script data. Every 0a title has index_only == 0; every 0b title has offset_only == 0; no title has any unclassifiable reference. ARI presence agrees in 45/45 — but nine titles have no ARI at all, so presence can never be the verdict, only a hint. The 46th title is 狂淫学園, which uses a different opcode entirely (§3.8) and resolves to 0a by the same rule once that opcode is read.

In 0a, a message record that no instruction references has no pointer to update when its length changes. Measured across all nine 0a titles:

3.3 tblstr.ari — the Type 0b index

u32 count            // = (number of type-0 records) + 1  <- note the +1, a Kaguya convention
u32 offset × (count - 1)
    // byte offsets of type-0 record HEADERS, in file order

Consistent in 39/39 files: header count matches, entry count matches, every offset lands exactly on a type-0 record header.

Regenerate this file wholesale on rebuild; do not patch it in place, and never ship the original alongside a rebuilt container.

3.4 Type 1 (STRTBL) — three files, one script

File header (16 B)
  "[STRTBL]"              // 8 B magic
  u32 count               // entry count; equals the parsed count in 6/6
  u32 unknown             // 0x00000001 in 6/6

Entries × count
  u32 id                  // sequential from 0 in 6/6
  u16 len
  u8  content[len]
        = ~(text + 0x00)                // the terminator IS inside the encrypted range
        + 0xFF ... padding              // 0xFF is the complement of 0x00

  len = round_up_4( len(text) + 1 + 6 ) - 6
// round_up_4
round_up_4(n) = (n + 3) & ~3

// Decode
dec  = xor_ff(content)
nul  = indexOf(dec, 0x00)
text = cp932_decode( nul >= 0 ? dec[0..nul] : dec )

// Encode
body = xor_ff( cp932_encode(text) )
if (original had a terminator) body += 0xFF        // = ~0x00
target = round_up_4(body.length + 6) - 6
body  += 0xFF × (target - body.length)
if (body.length > 0xFFFF) abort this entry         // u16 length field is a hard cap
The padding formula holds for every entry in all 6 Type 1 titles. Alignment samples: 妹汁 entries start at 16, 44, 92; 家庭教師 at 16, 40, 60.

Type 1 splits the job across three files and you need all three:

  • tblstr.arc — the strings, with no type information
  • scr.arc — a LINK3 container that says which string is a message and which is a choice, and attaches a speaker and a voice clip to each message
  • tblname.arc — the speaker table [MESNAM] and the resource manifest [F-NAME]

Every Type 1 container holds zero name records (6/6): names live entirely in [MESNAM].

Classification is exhaustive, and each entry is referenced exactly once (6/6)

3.5 tblname.arc — [MESNAM] and [F-NAME]

[MESNAM] (8 B)
  u16 pad = 0
  u16 count
  count × [ u16 len · CP932 name ]         // ** PLAINTEXT, not encrypted **

[F-NAME] (8 B)
  u32 entry_count
  u32 unknown = 1                          // 1 in 6/6
  entry_count × [ u16 len · XOR-0xFF data ]   // ** this section IS encrypted **
       trailing 0x00 after decryption is padding; strip it
The two sections use different encodings. [MESNAM] speaker names are plaintext CP932. [F-NAME] resource filenames are complement-encrypted. Getting this backwards produces garbage in one section and looks like a parser bug in the other.

The protagonist's MESNAM entry looks empty but is not. In player-named titles it contains the player-name marker bytes (§5), which render as nothing in game and as nothing in most hex viewers' text pane. No MESNAM entry in any of the six Type 1 titles is genuinely blank — all names are distinct and non-empty. Marker-bearing entries appear in exactly the three player-named titles (恥辱診察室, ナースにおまかせ, 家庭教師) and in none of the three fixed-name titles (妹汁 = 晶, ドキドキお姉さん = 智博, まほこい = 沙倉★誠志).

3.6 LINK3 scr.arc and its opcodes

"LINK3scr" (8 B) · record × N          // first record at offset 0x08

Record:
  u32 rec_len
  u16 0
  u16 year                             // ** the BUILD YEAR: 0x7D2 = 2002 **
  u8  mon, day, hh, mm, ss
  u16 namelen
  u8  0
  u8  name[namelen]                    // CP932
  "[SCR-FILE]" | "[SCR-Ver2]" | "[SCR-Ver3]"
  [u16 extra]                          // present ONLY for [SCR-FILE]
  u32 instr_size
  u8  instructions[instr_size]

Opcode frame:
  u16 opcode · u16 totalSize · payload(totalSize - 4)
  // match opcodes on the LOW BYTE only (op & 0xFF)

0x07 message payload — fully mapped

engine 0x7D2  (size 16 B, payload 12 B)   engine 0x7D3 / 0x7D4 / 0x7D5+  (size 20 B, payload 16 B)
  +0  u16  script-local counter            +0  u16  script-local counter
  +2  u16  ?                               +2  u16  ?
  +4  u16  SPEAKER -> [MESNAM]             +4  u16  ? (mostly 0xFFFF)
  +6  u16  VOICE   -> [F-NAME]             +6  u16  constant 0
  +8  u32  TEXT    -> STRTBL offset        +8  u16  SPEAKER -> [MESNAM]
                                           +10 u16  VOICE   -> [F-NAME]
                                           +12 u32  TEXT    -> STRTBL offset

// ** Tail-triple rule: one rule covers every version **
speaker_off = text_off - 4      sentinel 0xFFFF = narration (no speaker)
voice_off   = text_off - 2      sentinel 0xFFFF = unvoiced

Speaker, voice and text are the last three payload fields and are always adjacent. 0x7D3 grew the payload from 12 B to 16 B by inserting four bytes at +4, i.e. ahead of the tail triple — the script-local counter still reads at +0. Nothing in the triple moved relative to the end of the payload, which is why one rule works everywhere.

It only matters to a signature-scan fallback; a structural record-chain walk never consults it and succeeds on 8/8 files with every script closing exactly.

Classification rules

  • 0x07 message beats 0x08 choice. An entry referenced by both is a message.
  • 0x11 only fills gaps (set-if-absent semantics).
  • Speaker and voice are indices, not offsets — never patch them. They are read-only context. Speaker names are edited in [MESNAM]; voice clips are not editable.
  • Correlate the engine version against the build date. 恥辱診察室 released in 2002 but reports 0x7D4 (2004) because its script was rebuilt for the DVD EDITION.

3.7 Type 2 (UF01)

File header (8 B)
  u32 "UF01"              // 0x31304655 little-endian
  u32 index_pos           // absolute offset of the index table

Records × N, immediately after the header
  u32 type                // 0 = message, 2 = name, 3 = choice
  u32 len
  u8  ~text[len]          // ** text only. No terminator, no padding, no alignment **

@index_pos
  u32 index[N]            // absolute offset of each record HEADER
The script refers to entries by flat record index, not byte offset. Preserve the record count and their order and every reference stays valid no matter how much text length changes — you never read or write scr.arc for a Type 2 title. 
// Rebuild
write "UF01", then a 0 placeholder for index_pos
for i in 0..N-1:
    new_index[i] = current write position
    if entry i untranslated -> re-emit (type, len, original bytes) verbatim
    else:
        body = xor_ff(cp932_encode(text))
        if (original record had a terminator) body += 0xFF
        emit (type, body.length, body)
new_index_pos = current write position
write new_index[]
seek(4); write new_index_pos
Re-add the 0xFF terminator only if the original record had one. Evidence: in 気になる彼女のママは現役魔法少女, record 0 is 31 bytes ending in 0xF5 — that is ~0x0A, a newline, with no terminator following.

The value of the gate

The inst[2] == 0 condition holds in every sampled WFL1/LIN2 title (the voice-name length lives at inst[3]), making it a loss-free false-positive filter. The criterion for promoting a byte pattern to a real opcode is hit count == type-0 record count; incidental byte matches in other titles never meet it.

4 · Branch B — message.dat

A self-contained dialogue database: speaker names, voice filenames and choices in one file. scr.arc is not needed — the script references dialogue by index, and indices never move if you do not add or delete entries.

4.1 v00 / ver2 / ver3 — one grammar, three dialects

File:   header(18 or 19 B) · { u32 length · payload(XOR key if encrypted) } × N · trailing
        length == 0 OR length overruns EOF  =>  the stream ends; the rest is "trailing"

Block:  cstring format_name         // speaker name, or "" for narration
        u8      item_count
        extra_cstrings × cstring    // ** v00 only: 3 always-empty filler fields **
        item_count × (
            [u8 voice_count]        // ** ver3 only; 1 implied on v00 / ver2 **
            voice_count × cstring voice
            cstring message
        )
        tail                        // unconsumed bytes; preserve verbatim
v00 ≡ ver2 + three filler cstrings. ver3 ≡ ver2 + a per-item voice count. That is the entire difference. Verified byte-exact on 392,150 / 392,150 blocks.

v00 :  extra_cstrings = 3,  per_item_voice_count = false,
       header_size = 18,  enc_off = 0x10,  key_off = 0x11
ver2:  extra_cstrings = 0,  per_item_voice_count = false,
       header_size = 18,  enc_off = 0x11,  key_off = 0x11
ver3:  extra_cstrings = 0,  per_item_voice_count = true,
       header_size = 19,  enc_off = 0x11,  key_off = 0x12

Block classification

ConditionMeaningIdentity
item_count == 0standalone text — choice, menu label, chapter titlechoice_id; the text is format_name
item_count > 0, format_name == ""narrationdialogue_id
item_count > 0, format_name != ""spoken line, with speakerdialogue_id
Read item_count positionally. A tempting shortcut is to split each block on NUL bytes and infer the shape from how many fields you get. That approach silently skips every multi-item block — 3,038 blocks across the ten ver2/ver3 files, roughly 5,985 dialogue lines and 2,900 speaker names — and cannot represent a ver3 voice_count above 1 at all. That 3,038 decomposes exactly into the two failure modes: 2,947 multi-item blocks + 91 items carrying more than one voice name.

Verified invariants (12/12 files)

  • names + choices == block_count exactly — every block classifies, none falls through.
  • Zero blocks fail the grammar; zero have unparsed trailing bytes; zero trailing bytes after the final block.
  • messages − names == multi_item exactly, which forces every multi-item block to carry exactly two items — no block anywhere has three or more.
  • Maximum ver3 voice_count observed: 5 (アルバイトの先輩…), then 4 (エロティ課). v00 and ver2 are always 1, as the grammar requires.
Order is load-bearing. The script's opcode 7 references the block index directly. Block order and item order must never change. Do not sort, merge, or delete empty entries.

Reference read and rebuild

// Read
encrypted = (data[enc_off] != 0)
xor_key   = data[key_off]
pos = header_size
while (pos + 4 <= len(data)):
    length = u32 @ pos
    if (length == 0 or pos + 4 + length > len(data)) break
    raw = data[pos+4 .. pos+4+length]
    if (encrypted) raw = xor(raw, xor_key)
    blocks.push(raw)
    pos += 4 + length
trailing = data[pos..]

// Parse one block with a cursor — never with split()
parse_block(buf, profile):
    format_name = read_cstring()
    item_count  = read_u8()
    extras      = read_cstring() × profile.extra_cstrings
    items = []
    repeat item_count:
        vc     = profile.per_item_voice_count ? read_u8() : 1
        voices = read_cstring() × vc
        msg    = read_cstring()
        items.push({ voices, msg })
    tail = buf[cursor..]              // keep it, for byte-exact reconstruction

// Write: header + { u32 len · xor(payload, key) } × N + trailing
// Item count and item order must be identical to what you read.
Encoded text must not contain 0x00. It would terminate the cstring early and desynchronise the whole block grammar. Refuse the write and keep the original bytes for that field.

4.2 ver4.0 — four indexed tables

Header
  "[SCR-MESSAGE]ver4.0"     // 19 B
  u8  enc_flag  @0x13
  u8  key       @0x14
  // data begins at 0x15

NAMES
  u32 count
  count × [ u16 len · bytes(XOR key) ]            // CP932

CHOICES
  u32 count
  count × [ u16 len · bytes(XOR key) ]            // CP932

MESSAGES
  u32 count
  count × [ u32 blockLen · XOR(block) ]
      block =
        u32 textLen
        u8  text[textLen]                         // CP932
        u8  voiceCount
        voiceCount × ( UTF-16LE chars … 0x0000 )  // ** always UTF-16LE **

COMMANDS
  u32 count
  count × [ u32 id · u8 nParams · nParams × u32 msgIdx ]

<trailing bytes>    // unrecognized binary; see the note below

How a line gets its speaker: command.id indexes Names; params[] index Messages.

  • 0xFFFFFFFF is the "no speaker" sentinel, accounting for 34–49 % of command records across 44 files. A -1 default overflows a u32 writer.
  • Voice strings are always UTF-16LE, NUL-terminated, regardless of the encryption flag. The rest of the file is CP932.
  • Zero duplicate command references in 44/44 files — each message is referenced at most once.
  • Orphan messages (referenced by no command): 0–154 per file, and they are exactly the ones lacking a trailing newline.
// Reader skeleton
encrypted = data[0x13] != 0
key       = data[0x14]
seek(0x15)
names    = [ dec(read(u16())) for _ in range(u32()) ]
choices  = [ dec(read(u16())) for _ in range(u32()) ]
messages = []
for _ in range(u32()):
    body   = dec(read(u32()))
    tlen   = u32(body);  text = body.read(tlen)
    vc     = body.read_u8()
    voices = [ read_utf16le_until_0000(body) for _ in range(vc) ]
    messages.push({ text, voices })
commands = []
for _ in range(u32()):
    cid = u32();  n = u8()
    commands.push({ id: cid, params: [u32() × n] })
tail = read_rest()          // not part of any table above
The bytes after the Commands table are unrecognized binary. 43 of 44 ver4 files carry 5,270 B – 1,393,427 B there, 18.9 MB in total. It corresponds to no table described above: unrelated titles carry byte-identical trailing data referencing message indices that exist in neither file. One file in the corpus (a trial build of ママトモ) has a zero-length tail, so the format does not require it. Stop reading at the end of the Commands table and treat anything beyond as opaque; the safe default when rebuilding is to omit it. Save it to a sidecar file if you want to keep it for inspection.
Linkage is positional, end to end. Script opcode 7 → Commands[i] → params[] → Messages[idx]. Every step is an array position. Adding, deleting or reordering a single entry breaks the script silently — the game will not crash, it will show the wrong line. Rebuild tables by id, never by append order, and abort on any table-count change.

Do not use file size as identity. Eleven unrelated titles share exactly 3,327,791 bytes. Compare hashes.

Both live in the CP932 0xF0–0xF9 EUDC (end-user defined character) range, which ordinary Japanese text cannot produce, so they are unambiguous. An audit of 34 message.dat files found 92,185 + 6,487 occurrences with zero straddling a character boundary.

Corpus census across 133 files: F0 40 in 58, F0 41 in 36, and 22 carrying F0 40 alone. F0 41 never appears without F0 40 — 133/133. Family-name substitution implies given-name substitution; the converse does not hold. Markers appear in tblstr.arc and tblname.arc as well as message.dat, from 2001-11-22 onward.
